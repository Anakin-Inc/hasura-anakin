# Hasura ndc-hub — submission instructions

Real structure, read directly from `hasura/ndc-hub` and its reference
connectors (`gh api` / raw GitHub, not assumed) — but the biggest lift here
isn't code, it's the two-repo, two-stage packaging pipeline, and one open
question about whether ndc-hub currently accepts third-party namespaces at
all. Read the whole file before treating this as "PR-ready" the way the
Fivetran/Dagster siblings are.

## What was researched (cite-checked, not guessed)

- `hasura/ndc-hub` root: `README.md`, `registry/`, `connector-metadata-types/`,
  `registry-automation/`, `rfcs/`, `ddn-workspace/`. No `CONTRIBUTING.md` —
  the README's "Adding e2e tests for your connector" section is the closest
  thing to a contribution guide.
- `registry/` contains exactly one namespace directory: `hasura/`, with 43
  connectors under it (athena, bigquery, http, openapi, sendgrid, stripe,
  postgres, snowflake, ...). Confirmed via the full recursive git tree, not
  a partial listing.
- Read `registry/hasura/stripe/` and `registry/hasura/http/` in full:
  `metadata.json`, `README.md`, `releases/vX.Y.Z/connector-packaging.json`,
  `tests/test-config.json`, `tests/compose.yaml`,
  `tests/snapshots/query*/{request.graphql,response.json,variables.json}`.
- `connector-packaging.json`'s `uri` points to a GitHub Release asset
  (`connector-definition.tgz`) hosted in a **separate** repo
  (`github.com/hasura/ndc-stripe`, `github.com/hasura/ndc-http`) — ndc-hub
  itself never contains connector source or Docker build context.
- Read `hasura/ndc-stripe` in full: `Dockerfile` (`FROM
  ghcr.io/hasura/ndc-http:v0.10.0` + `COPY ./config /etc/connector` — three
  lines, no code), `config/config.yaml` (runtime `ndc-http` config),
  `generator/config.yaml` (points at Stripe's own published OpenAPI spec),
  `Makefile` (`ndc-http-schema convert` / `update` targets),
  `docker-compose.yaml`, `.env.example`. Confirms `ndc-http` + a vendor's
  OpenAPI spec is Hasura's own pattern for wrapping a REST API, not a
  workaround invented for this submission.
- Read `hasura/ndc-http`'s `README.md`, `docs/authentication.md`, and
  `docs/configuration.md` for the exact `securitySchemes` YAML shape
  (`type: apiKey`, `in: header`, `name`, env var auto-generated from
  `envPrefix` + scheme key) and confirmation that `files:` entries can
  reference an OpenAPI 3 document **directly at runtime**
  (`spec: oas3`) — pre-converting to a static `schema.json` via the
  `ndc-http-schema` CLI is an optimization, not a requirement.
- Checked `connector-metadata-types/schema.json` and `connectorTypes.ts` for
  the `connector-metadata.json` shape that goes *inside* the release tarball
  (`packagingDefinition`, `supportedEnvironmentVariables`, `commands`,
  `dockerComposeWatch`) — that file is generated by Hasura's own build
  tooling (`ddn connector build`), not hand-written; not fabricated here.

## The finding that matters most

Every entry under `registry/` is namespaced `hasura` — including a "new
connector" PR merged during this research (#717, `manasag`, "Posthog
connector," source repo `github.com/hasura/promptql-posthog` — still a
Hasura-owned repo). The last 15 merged PRs to `ndc-hub` are all Hasura-team
releases of existing connectors. There is **no observed instance** of an
outside company self-publishing a new top-level namespace via PR, and no
`CONTRIBUTING.md` describing that path.

This doesn't mean it's impossible — `metadata.json`'s schema has no
namespace allowlist, `is_hosted_by_hasura`/`is_verified` are plain booleans,
and the README's beta warning ("subject to large changes... feedback is
welcome, [file] an issue") reads as genuinely open. But in practice this
registry today functions as Hasura's own curated connector catalog, not an
open marketplace the way `fivetran/community_connectors` or
`dagster-io/community-integrations` are. **Opening an issue with Hasura
first, before building the release pipeline below, is the realistic first
step** — not filing a cold PR and hoping it's merged.

## Verified, not assumed

- `python3 -m json.load` and `yaml.safe_load` pass clean on every JSON/YAML
  file in this directory (`anakin.openapi.json`, `config.yaml`,
  `metadata.json`, `connector-packaging.json`, `test-config.json`,
  `compose.yaml` ×2, all 5 WireMock mapping files, all 10
  `variables.json`/`response.json` snapshot files) — see the verification
  log below.
- `anakin.openapi.json` checked against the OpenAPI 3.0.3 structural rules
  `ndc-http`'s docs describe: `servers`, `security` +
  `components.securitySchemes.api_key` (`type: apiKey`, `in: header`,
  `name: X-API-Key`), every path has `operationId` + `responses.200.content`.
- Every field name in the OpenAPI request/response schemas
  (`url`, `country`, `useBrowser`, `generateJson`, `forceFresh`, `sessionId`,
  `sessionName`, `prompt`, `limit`, `schema`, and the full `Document` /
  `SearchResult` / `AgenticSearchResult` response shapes) is copied from
  `anakin-py/src/anakin/client.py` and `models.py`, not invented.
- `config/config.yaml`'s shape (`output`, `strict`, `forwardHeaders`,
  `concurrency`, `files[].{file,spec,envPrefix,timeout,retry}`) matches
  `ndc-stripe/config/config.yaml` and `ndc-http/docs/configuration.md`
  field-for-field.

## Not done — needs tooling unavailable in this sandbox, or a real release

- **Never run `ndc-http` itself.** No Docker in this sandbox, so
  `docker-compose up --build` in `connector/` was never executed, and the
  OpenAPI → NDC schema transform (`GET /schema` on the running connector)
  was never actually exercised. The generated GraphQL field names in the
  snapshot fixtures (`submitUrlScraper`, `getUrlScraperJob`, `search`,
  `submitAgenticSearch`, `getAgenticSearchJob`) are the connector's
  `operationId`s carried straight through, which is `ndc-http`'s documented
  default behavior — but only running the connector confirms it.
- **`connector-packaging.json`'s `uri`/`checksum`/`source.hash` are
  placeholders, deliberately marked `TODO`, not fabricated values.** These
  can only be real after: (1) a real `github.com/anakin-io/ndc-anakin` repo
  exists with `connector/`'s contents, (2) a GitHub Release is cut from it,
  (3) `ddn connector build create` (or equivalent packaging step referenced
  by `connector-metadata-types/`) produces `connector-definition.tgz`, and
  (4) that asset is uploaded and sha256'd. None of steps 1–4 are things this
  sandbox can do (no external repo creation, no Hasura CLI, no ability to
  cut a GitHub release).
- **WireMock stack never run** — no Docker. The mapping files are
  structurally valid JSON and the request/response shapes match ground
  truth, but "the e2e test actually passes" is unverified.
- **Pre-compiling `anakin.openapi.json` to a static `schema.json` via
  `ndc-http-schema convert`** (the `ndc-stripe` pattern) needs a Go
  toolchain — not attempted; the runtime-direct-OpenAPI mode used instead is
  documented and supported, just unbenchmarked.
- **No live Anakin API key was used anywhere** — every response fixture is
  a hand-built canned value shaped like the real SDK models, not a captured
  real response.

## Steps (needs the account owner)

1. **Open an issue on `hasura/ndc-hub` first** describing the connector and
   asking whether third-party-namespaced submissions are currently accepted
   — given the "no precedent" finding above, this de-risks the rest of the
   work before investing in a release pipeline.
2. Stand up `github.com/anakin-io/ndc-anakin` (or similar) from
   `connector/`'s contents. Run `docker-compose up --build` locally against
   a real `ANAKIN_API_KEY`, confirm `/schema` and a few live queries work.
3. Cut a `v0.1.0` GitHub Release; build and upload
   `connector-definition.tgz` per Hasura's packaging tooling (`ddn`
   CLI — see `connector-metadata-types/README.md` and the `rfcs/000{1,4}-*`
   packaging RFCs for the exact steps).
4. Fill in `registry-entry/releases/v0.1.0/connector-packaging.json`'s real
   `uri`, `checksum.value` (sha256 of the actual tarball), and
   `source.hash` (the release commit).
5. Add a real `logo.png`.
6. Stand up the WireMock stack, run it against the `e2e-testing` runner
   locally to confirm the snapshots actually pass (the [PR #485
   pattern](https://github.com/hasura/ndc-hub/pull/485/files) the ndc-hub
   README points to as the worked example).
7. Fork `hasura/ndc-hub`, add `registry-entry/`'s contents at
   `registry/anakin/anakin/`, open the PR.
